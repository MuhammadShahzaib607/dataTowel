================================================================================
                         DATATOWEL — PROJECT SUMMARY
================================================================================

DataTowel is a full-stack e-commerce web application for a premium bulk textile
supply business based in Pakistan. It supplies cotton towels, bedsheets, and
linens in bulk to hotels, restaurants, gyms, and retailers. The application
features a public storefront, user dashboard, and admin dashboard with complete
order management, payment verification, notification system, blog management,
and soft-delete/trash functionality.

================================================================================
1. PROJECT OVERVIEW
================================================================================

- Brand: DataTowel
- Tagline: "Premium Bulk Textile Supply"
- Market: Pakistan (bulk/business customers)
- Currency: PKR (₨)
- Products: Cotton towels and bedsheets in various sizes and categories

================================================================================
2. TECHNOLOGY STACK
================================================================================

Frontend (client/):
  - Framework: Next.js 15 (App Router)
  - Language: TypeScript
  - State Management: Redux Toolkit (with Redux slices for auth, cart, wishlist, UI)
  - Styling: Tailwind CSS
  - Animations: Framer Motion
  - Icons: Lucide React
  - Authentication: Firebase Client SDK (Google Auth) + custom JWT auth
  - HTTP Client: Native fetch API with custom wrapper

Backend (server/):
  - Runtime: Node.js
  - Framework: Express.js
  - Language: JavaScript (ES Modules)
  - Database: MongoDB (Mongoose ODM)
  - Authentication: JWT (jsonwebtoken) + Firebase Admin SDK (Google token verification)
  - File Uploads: Multer (memory storage)
  - Image Hosting: Cloudinary
  - Email Service: Nodemailer (Gmail SMTP)
  - Security: bcryptjs for password hashing

4. DATABASE MODELS
================================================================================

User
  - username (String, required)
  - email (String, required, unique, lowercase)
  - password (String, optional for Google users, hashed with bcrypt)
  - isAdmin (Boolean, default false)
  - isVerified (Boolean, default false)
  - firebaseUid (String, unique, sparse — for Google auth)
  - authProvider (String: "local" | "google")
  - firstName, lastName, phone, city, country (String, profile fields)
  - profileImage (String, URL)
  - emailVerificationOtpHash, emailVerificationOtpExpires (for email verification)
  - timestamps (createdAt, updatedAt)

Product
  - name (String)
  - description (String, maxlength 2000)
  - category (String — "Towels" or "Bedsheets")
  - subCategory (String — e.g. "Bath Towel", "Single Bedsheet")
  - sizes ([String] — array of available sizes)
  - price (Number, nullable)
  - discountedPrice (Number, nullable)
  - images ([{ url, publicId }] — Cloudinary images)
  - isActive (Boolean, default true)
  - timestamps
  - Indexes: isActive+category, text on name

Order
  - orderNumber (String, unique — format "DT-XXXXX")
  - customer (ObjectId → User)
  - customerName, customerEmail (String)
  - items ([{ product, name, size, quantity, price, total }])
  - subtotal (Number)
  - deliveryCharge (Number)
  - totalAmount (Number)
  - city (String)
  - paymentMethod (String: "manual_transfer" | "cod")
  - notes (String, maxlength 500)
  - paymentStatus (String: "pending" | "submitted" | "verified" | "rejected")
  - paymentProof ({ imageUrl, imagePublicId, submittedAt })
  - bankDetails ({ accountTitle, bankName, accountNumber, iban }) — snapshot at order time
  - orderStatus (String: "pending_payment" | "processing" | "dispatched" | "delivered" | "cancelled")
  - statusHistory ([{ status, changedAt, changedBy }])
  - cancellationReason (String)
  - paymentRejectionReason (String)
  - isActive (Boolean, default true)
  - isDeleted (Boolean, default false — soft delete)
  - deletedAt (Date, nullable)
  - deletedBy (String)
  - timestamps
  - Indexes: customer+createdAt, isActive+createdAt, isDeleted+createdAt, orderNumber

Notification
  - type (String, indexed — e.g. "new_order", "payment_verified", "order_status_update")
  - title (String, required)
  - message (String, required)
  - userId (ObjectId → User, required)
  - orderId (ObjectId → Order, required)
  - reason (String)
  - link (String — URL path to navigate to)
  - isRead (Boolean, default false, indexed)
  - timestamps
  - Indexes: createdAt, userId+isRead+createdAt, orderId+type

Blog
  - title (String, maxlength 300)
  - excerpt (String, maxlength 500)
  - content (String, maxlength 50000)
  - category (String)
  - images ([{ url, publicId }])
  - isActive (Boolean, default true)
  - timestamps
  - Indexes: isActive+createdAt, category, text on title+content

BankDetails (singleton — only one record allowed)
  - accountTitle, bankName, accountNumber, iban (String)
  - timestamps

DeliverySettings (singleton — only one record allowed)
  - karachiCharge (Number, default 300)
  - outsideKarachiCharge (Number, default 500)
  - timestamps

5. AUTHENTICATION & AUTHORIZATION
================================================================================

Registration Flow:
  1. User submits username, email, password
  2. Server creates user with isVerified=false
  3. Server generates 6-digit OTP, hashes it with SHA-256, stores hash + expiry (10 min)
  4. Server sends verification email via Gmail SMTP (Nodemailer)
  5. User submits OTP → server compares hash → sets isVerified=true → returns JWT

Login Flow:
  1. User submits email + password
  2. Server verifies credentials and isVerified status
  3. If email not verified, returns 403 with code "EMAIL_NOT_VERIFIED"
  4. On success, returns JWT (expires in 7 days by default)

Google Login Flow:
  1. Client uses Firebase Auth to get Google ID token
  2. Client sends ID token to server
  3. Server verifies token with Firebase Admin SDK
  4. Server finds or creates user by firebaseUid or email
  5. Returns JWT

Middleware:
  - authMiddleware: Verifies JWT, attaches user to req.user (any logged-in user)
  - adminAuthMiddleware: Verifies JWT + checks user.isAdmin (admin only)

Password Security:
  - Passwords hashed with bcrypt (salt rounds: 10)
  - Password field has select: false (excluded from queries by default)

JWT:
  - Signed with JWT_SECRET
  - Stored in localStorage on client as "datatowel_token"
  - Auth state persisted via AuthInitializer + restoreUser thunk

8. BUSINESS FLOWS
================================================================================

Customer Purchase Flow:
  1. Browse products at /products
  2. View product details, select size
  3. Add to cart (persisted in localStorage)
  4. View cart (CartDrawer or /cart)
  5. Proceed to checkout (/checkout)
  6. Fill customer info (name, email, phone, city, address)
  7. Select city (Karachi vs other — affects delivery charge)
  8. Select payment method (Manual Bank Transfer)
  9. View bank details, make transfer
  10. Place order → order created with paymentStatus: "pending", orderStatus: "pending_payment"
  11. After placing order, upload payment screenshot from order details page
  12. Order paymentStatus changes to "submitted"
  13. Admin reviews and verifies/rejects payment
  14. If verified: orderStatus moves to "processing"
  15. Admin updates status: processing → dispatched → delivered
  16. User receives notifications at each status change

Admin Management Flow:
  1. Login as admin
  2. View dashboard with stats (products, orders, revenue)
  3. Manage products (CRUD, categories, images, pricing)
  4. Manage orders (view, filter, verify/reject payments, update status)
  5. Manage users (view list, details)
  6. Manage blogs (CRUD, images)
  7. Manage notifications (view, mark read)
  8. Configure settings (bank details, delivery charges)

Order Cancellation Flow:
  1. User views order details
  2. Clicks "Cancel Order" (only before dispatched)
  3. Provides cancellation reason (required)
  4. Order status → "cancelled", isActive → false
  5. Admin receives notification

Payment Verification Flow:
  1. User uploads payment screenshot
  2. Image uploaded to Cloudinary, stored on order
  3. paymentStatus → "submitted"
  4. Admin receives notification
  5. Admin views order, sees screenshot
  6. Admin verifies → paymentStatus: "verified", orderStatus: "processing"
     OR Admin rejects → paymentStatus: "rejected", with rejection reason
  7. User receives notification of verification/rejection

Soft Delete / Trash Flow:
  1. User/Admin clicks "Move to Trash" on an order
  2. Confirmation dialog appears
  3. On confirm: isDeleted=true, deletedAt=now, deletedBy=userId
  4. Order disappears from normal list
  5. Order appears in Trash tab
  6. User/Admin can Restore → isDeleted=false, deletedAt=null
  7. Order returns to normal list
  8. Backend always filters out deleted orders by default

Email Verification Flow:
  1. User registers with email/password
  2. 6-digit OTP generated, hashed with SHA-256, stored with 10-minute expiry
  3. Verification email sent via Gmail SMTP
  4. User enters OTP
  5. Server compares hash → marks user as verified → returns JWT
  6. User can resend OTP (invalidates previous)

9. IMPORTANT BUSINESS RULES & BEHAVIOR
================================================================================

User Permissions:
  - Users can only view/edit their own profile
  - Users can only view their own orders
  - Users can only cancel their own orders (before dispatched)
  - Users can only upload payment proofs for their own orders
  - Users can only soft-delete/restore their own orders
  - Users cannot access admin routes

Admin Permissions:
  - Admin can manage all products (CRUD)
  - Admin can manage all orders (view, update status, verify/reject payments, soft delete)
  - Admin can manage all users (view)
  - Admin can manage all blogs (CRUD)
  - Admin can manage notifications
  - Admin can configure bank details and delivery charges
  - Admin can soft-delete and restore any order

Order Cancellation Rules:
  - Can only cancel before "dispatched" status
  - Cancellation reason is required
  - Order isActive → false on cancellation
  - Admin receives notification

Payment Rules:
  - Payment screenshot upload only before "verified" or "cancelled"
  - Payment rejection requires a reason
  - Cannot move to processing/dispatched/delivered without verified payment
  - Cannot cancel after dispatched

Delivery Charge Rules:
  - Karachi: configurable rate (default ₨300)
  - Outside Karachi: configurable rate (default ₨500)
  - Delivery charge calculated server-side based on selected city
  - City selection via searchable dropdown

Notification Behavior:
  - Admin notifications: created for new orders, payment uploads, cancellations
  - User notifications: created for payment verification, rejection, status updates
  - Notifications include order link for quick navigation
  - Real-time unread count sync via custom event bus (window events)
  - 30-second polling for unread count updates
  - Notification cards are clickable (navigate to order)

Soft-Delete / Trash Behavior:
  - Orders are never permanently deleted
  - isDeleted=true, deletedAt=timestamp, deletedBy=userId
  - Normal queries exclude deleted orders by default (isDeleted: {$ne: true})
  - Trash tab shows only deleted orders (isDeleted=true)
  - Restore sets isDeleted=false, deletedAt=null, deletedBy=""
  - Both admin and users have their own Trash tabs
  - Backend enforces ownership on user-side trash/restore

Product Rules:
  - Products have categories (Towels, Bedsheets) and subcategories
  - Products can have multiple sizes
  - Products can have multiple images (Cloudinary)
  - Products support discounted pricing
  - isActive flag controls public visibility

Notification Unread Count:
  - Sidebar badge shows unread count
  - Updates instantly via event bus when notifications are marked as read
  - Works across admin and user dashboards

Sidebar Collapse:
  - Both admin and user dashboards support sidebar collapse/expand
  - State persisted in localStorage
  - Collapsed: icons only, tooltips on hover
  - Expanded: icons + labels
  - Smooth CSS transition

Clickable Lists:
  - Order list items (admin + user) are fully clickable
  - Notification list items (admin + user) are fully clickable
  - Action buttons inside use e.stopPropagation() to prevent navigation conflicts

10. IMAGE HANDLING
================================================================================

- All images uploaded via Multer (memory storage, 5MB limit)
- Allowed types: JPEG, PNG, WebP
- Uploaded to Cloudinary with transformations:
  - Products: folder "datatowel/products", format webp, quality auto
  - Blogs: folder "datatowel/blogs", format webp, quality auto
  - Profiles: folder "datatowel/profiles", 500x500 crop, face gravity, format webp
  - Payments: folder "datatowel/payments", format webp, quality auto
- Old images deleted from Cloudinary on replacement/delete
- Public IDs stored for cleanup
